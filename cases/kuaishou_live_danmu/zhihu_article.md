## 一、弹幕到底是怎么来的？先把架构吃透

### 1.1 一个反直觉的事实：没有弹幕接口

很多人第一反应是"弹幕肯定是轮询某个接口刷出来的"。打开 DevTools 的 Network 面板，按 `comment` / `danmu` / `msg` 过滤——**什么都没有**。

为什么？因为弹幕走的是 **WebSocket 长连接**。Network 面板默认只列 HTTP 请求，WS 帧藏在单独的 **WS 标签页**里，不看 WS 标签页你根本找不到弹幕在哪。

> **第一个认知门槛**：找弹幕，先看 Network → WS，不是 XHR。

### 1.2 完整链路（三段式）

蹲在 WS 标签页里逐帧看，再对照前端代码，链路还原如下：

```text
① HTTP  GET /live_api/liveroom/websocketinfo?caver=2&liveStreamId=<id>&__NS_hxfalcon=<签名>
        → { token, websocketUrls: [wss://...] }          // 一次性拿连接凭证

② WSS   连 websocketUrls[0]
        → 客户端发"进房帧"：
          SocketMessage{ payloadType=200, payload=CSWebEnterRoom{token, liveStreamId, pageId} }

③ 服务端持续推送（全是 protobuf 二进制）：
        829=文本弹幕  310=礼物  340=进场  101=在线人数  510=点赞  300=进房ACK
```

三个关键认知：

1. **弹幕不是拉的，是推的**。你只需进房"订阅"，之后服务端源源不断推。
2. **一切皆 protobuf 二进制**，不是 JSON。payload 外面还套了**应用层 gzip**。
3. **`websocketinfo` 要带自定义签名** `__NS_hxfalcon`，没有它直接 `result=2`。

所以整条链路要攻克三关：**签名**、**WebSocket 连接**、**protobuf 解码**。但真正动手后发现，还有一道看不见的墙——**TLS 指纹**。下面按我实际踩坑的顺序讲。

## 二、第一关：TLS 指纹——协议全对，照样断你连（最隐蔽的坑）

这是整场逆向里**最隐蔽、最能体现道行**的一关。

### 2.1 诡异的现象

我先把协议帧搞定（后面讲），本地 Python 连上 WSS，进房帧和浏览器抓包**逐字节一致**。结果：

> **服务端一发业务帧就把我断了。但空连接能一直活着。**

这句话信息量很大，拆开看：

- TCP 三次握手 ✅ 成功
- TLS 握手 ✅ 成功（证书校验都过了）
- WS Upgrade ✅ 成功
- 我发进房帧 → **服务端把连接关了**

协议帧明明和浏览器一模一样，为什么？

### 2.2 排查过程：逐步排除

我按"由表及里"排除了几种可能：

1. **怀疑帧格式错**：逐字节比对抓包，**完全一致**，排除。
2. **怀疑缺 Header**：补上 `Origin` / `User-Agent` / `Cookie`，仍被断，排除。
3. **怀疑发太快**：加延时、先发心跳，仍被断，排除。
4. **关键对照实验**：**只连不发**，连接能活几十秒；**一发任意帧**（哪怕是无意义的一字节），立刻被断。

第 4 点是破局点：**断开与"帧内容"无关，只与"发了帧"这个动作相关**。这说明服务端不是在校验你的帧，而是在**校验"你"这个客户端本身**。

### 2.3 根因：JA3 指纹

答案是大厂在 **TLS 握手阶段**就给你拍了指纹——**JA3**。

JA3 把 TLS ClientHello 的**版本、加密套件顺序、扩展列表、椭圆曲线、扩展格式**拼成一个字符串再做 MD5，得到一个哈希。同一个库发出的 ClientHello 高度一致，所以 JA3 能稳定识别"你是 Chrome 还是 Python requests"。

Python `ssl` / `requests` 的 ClientHello 和 Chrome 长得**完全不同**。服务端在握手时就算好了你的 JA3，**先放你进来**（握手不做业务拦截），**等你发业务帧时**才拿 JA3 对账——不是浏览器指纹，踢。

这解释了那个诡异现象：**握手阶段不拦（所以连得上），业务帧触发校验（所以一发就断）**。

### 2.4 破解

用一个能**伪造 Chrome TLS 指纹**的客户端。业界主流是 **curl-impersonate**（复刻了 Chrome/Firefox/Safari 的 TLS 指纹），Python 封装是 `curl_cffi`：

```python
from curl_cffi import requests
session = requests.Session(impersonate="chrome")   # 伪造 Chrome 的 JA3
ws = session.ws_connect(wss_url, headers={"Origin": "...", "Cookie": cookie})
```

换上之后，**同样的帧，服务端就认了**。

> **这一关的通用经验**：当你的协议帧和抓包**逐字节一致却仍被断连**，且**空连接能活、业务帧一到就断**——**别再怀疑协议，先怀疑 TLS 指纹**。这是大厂长连接风控的第一道暗桩。同理，HTTP 层被风控也可优先考虑 JA3。

## 三、第二关：自定义签名 `__NS_hxfalcon`——JSVMP 里藏着一整套密码学

请求 `websocketinfo` 必须带签名 `__NS_hxfalcon`，格式是**两段拼接**：`HUDR_<base64url>$HE_<hex>`。

### 3.1 定位：签名是哪个函数生成的

先定位签名入口。两个办法：

1. **搜参数名**：在已加载脚本里全局搜 `__NS_hxfalcon`，找到拼 URL 的地方。
2. **XHR 断点回溯**：在 `websocketinfo` 请求上打 XHR 断点，触发后看调用栈，往上回溯到"给 URL 拼签名"的那一层。

追进去发现，签名由一个 `$encode` 之类的函数生成，但这个函数体在源码里**根本看不到逻辑**——它被 **JSVMP 虚拟机**包住了。

### 3.2 JSVMP 是什么，为什么难

**JSVMP（JS Virtual Machine Protection）**：把原始 JS 编译成一段**自定义字节码**，再塞进一个**解释器**里逐条执行。你在源码里看到的只剩类似这样的东西：

```javascript
function _ace_37b52(p0, p1, p2, p3, p4, p5, p6) {
  var _ace_043 = [ [op, a, b, c], [op, a, b], ... ];   // opcode 表
  while (pc < _ace_043.length) {
    var inst = _ace_043[pc];
    handlers[inst[0]](inst[1], inst[2], inst[3], ...);  // opcode 分发
  }
}
```

**肉眼完全读不出业务逻辑**——真正的算法藏在字节码的执行序列里。这是当下对抗静态逆向**最狠**的手段之一，因为 AST 解混淆对它基本无效（代码本身没被混淆，只是被"翻译"成了虚拟机指令）。

### 3.3 破局：不死磕字节码，走"动态 + 参照"双线

硬还原 JSVMP 字节码成本极高。我走的是两条更聪明的线：

**线 A：动态插桩，对齐"输入 → 输出"。** 不关心虚拟机内部怎么跑，只在 `$encode` 的**入口和出口**插桩，记录"给定输入 X，输出是什么"。只要我本地实现能对同样的输入产出同样的输出，就算还原成功——**黑盒对齐即可，不必白盒复刻**。

**线 B：参照社区实现。** 这类大厂签名往往已有开源参照（搜算法特征/常量）。找到后对照其结构，快速确认算法骨架。

### 3.4 算法骨架（常量已脱敏）

最终还原出的算法结构，两段分别是：

**`$HE_` 段**（签名主体）：

```text
1) 拼输入：signInput + "HUDR_" + HUDR体
   （signInput = 路径 + 排序后的 key=value 直接拼接，去掉签名自身）
2) BLAKE2s 变体：IV 被魔改、参数块首字节异或，非标准 BLAKE2s
3) LFSR 流变换：线性反馈移位寄存器，种子固定，逐字节异或派生流
4) 取前若干字节，异或一个 4 字节固定掩码 → hashField
5) 拼 preHex = 固定头 + startup随机(小端) + 48位随机(小端)
              + (计数 ^ 魔数)(小端) + hashField + (时间戳 ^ 魔数)(小端) + 固定尾 + LRC
6) 最终变换：以末字节为 key，对前面字节流式异或 → hex
```

**`HUDR_` 段**：

```text
1) 打包：脚本数、计数器、调用栈尾等
2) 逐字节异或 0x23
3) ChaCha20 变体：key/nonce 硬编码、计数器从 1 起、常量非标准（非标准 ChaCha）
4) Base64URL（+/= 换成 -_.）
```

一句话：**BLAKE2s 变体 + LFSR + ChaCha20 变体 + 多重异或 + LRC**，全硬编码常量，纯算法可复现。

### 3.5 两个能省命的前置判断

动手还原前，先确认两点，能省大量功夫：

1. **签名是否可复用（非一次性 nonce）**：拿同一个签名连发几次，如果服务端都认，说明不是一次性 nonce，可以复用。本平台**可复用**。
2. **signInput 的精确拼法**：`key=value` 怎么排序、要不要编码、要不要去掉签名自身——拼错一个字符签名就废。**以抓包请求反推**，别猜。

> **这一关的通用经验**：遇到 JSVMP 别硬刚字节码。**动态插桩对齐输入输出 + 找参照实现**，先黑盒对齐再谈还原。**先验证签名可复用、确认 signInput 拼法**，再动手。

## 四、第三关：设备指纹 Cookie——这个真伪造不了，我认了

请求还要带一个访客身份 Cookie（形如 `kwfv1`）。我一开始想本地生成，结果两条路都被堵死：

1. **在 Node 沙箱里跑官方指纹 SDK** → 直接报 `Failed to process fingerprint`。
2. **自己随便造一个身份** → 服务端反手一个 `result=400002` + 验证码挑战。

### 4.1 深挖：为什么伪造不了

追这个 SDK，发现它也是一套 **JSVMP 指纹采集器**，会采集一堆**真实设备特征**：

- **canvas 指纹**：画一段文字+图形，取 `toDataURL` 的哈希
- **WebGL 指纹**：`renderer` / `vendor` / 支持的扩展
- **字体枚举**、**AudioContext 指纹**、`navigator` 各种属性……

这些特征拼起来算出设备指纹。关键在于：**沙箱里这些 API 全是假的**。Node 里没有真实 canvas/GPU，算出来的指纹要么报错、要么是"一眼假"的默认值，服务端风控直接拦。

### 4.2 务实的选择：采集 + 缓存

这是本次逆向**唯一的"不可本地化"环节**。我的处理很务实：

> **从真实浏览器一次性采集这个 Cookie，落盘缓存，之后复用。**

设备指纹通常**有效期很长**（天级甚至更久），采集一次能用很久，性价比极高。

> **这一关的通用经验**：设备指纹类 Cookie（canvas/WebGL/音频采集的那种）**别想着本地伪造**，正路是"**采集 + 缓存**"。**认清哪些能本地化、哪些不能**，是逆向工程师和"脚本小子"的分水岭。硬刚一个"设计上就不该能伪造"的东西，是浪费时间。

## 五、第四关：protobuf 解码——字段位置，信实测别信猜

弹幕 payload 是 **protobuf 二进制**，外面还套了一层**应用层 gzip**（`1f 8b` 开头）。处理顺序：**先 gzip 解压，再解 protobuf**。

### 5.1 protobuf 基础：varint + tag

protobuf 每个字段是 `tag + value`。tag 由 **字段号 + wire 类型**组成，用 **varint**（变长整数）编码：

```text
tag = (field_number << 3) | wire_type
wire_type: 0=varint  2=length-delimited(bytes/string)  1=64位  5=32位
```

比如 `0x0A` = `0000 1010` → 字段号 1、wire 类型 2（bytes）。读懂 varint 和 tag，就能手工剥 protobuf。

### 5.2 踩坑一：字段位置，信实测别信猜

我从混淆代码里静态推断弹幕文本在 `field 3`，结果死活解不出来。抓**真实帧**逐字节比对后才发现，弹幕文本在**嵌套结构**里：

```text
829 帧（gzip 解压后）
└─ f1: zone 消息
   ├─ f1(str) = 房间会话 id
   └─ f7: 消息容器
      └─ f1 (repeated): 单条消息
         ├─ f1(str) = ★ 弹幕文本    ← 文本藏在这，不是顶层 field 3
         └─ f2(msg) = 用户信息
```

**血泪教训**：protobuf 字段位置**以抓包实测为准**。混淆代码里的静态推断**不可信**——字段号可能被重排、有嵌套、有可选字段。

### 5.3 踩坑二：弹幕其实大多是礼物帧

这是最坑的**认知陷阱**：我在一个游戏直播间蹲了半天，文本弹幕(829)几乎不出现，一度以为实现有 bug。后来才想明白——

**弹幕区滚动的内容，大部分是礼物帧(310)和进场帧(340)**，纯文本弹幕(829) 在冷门/游戏直播间**非常稀疏**（大家都在看操作，不打字）。

所以正确的做法是**全类型解码**：

```text
829=文本弹幕  310=礼物(含弹幕文本)  340=进场/用户列表
101=在线人数  510=点赞  300=进房ACK
```

把 310/340 也解出来，输出立刻就丰富了。**只解文本帧，会把"稀疏"误判成"失败"**。

> **这一关的通用经验**：protobuf 字段位置**以实测为准**；**全类型解码**，别只盯着你想要的那一种帧，否则会把"数据稀疏"误判成"实现错了"。

## 六、调试实录：我是怎么一步步定位的（授人以渔）

把完整的排查思路复盘一遍，这套流程可以迁移到绝大多数协议逆向：

```text
Step 1  抓包定架构
        Network→WS 找到弹幕通道；确认"拉 or 推"、"二进制 or JSON"

Step 2  定位签名
        搜参数名 __NS_hxfalcon / XHR 断点回溯调用栈 → 找到 $encode 入口

Step 3  判断防护等级
        发现 $encode 是 JSVMP → 放弃静态还原，改"动态对齐 + 参照实现"

Step 4  先做对照实验
        连上就断 → 逐字节比对帧(排除协议) → 补Header(排除缺头)
        → 空连接能活/发帧就断 → 锁定 TLS 指纹

Step 5  逐层攻破
        TLS 指纹(curl_cffi) → 签名(算法还原) → 设备指纹(采集+缓存)
        → protobuf(实测字段) → 全类型解码

Step 6  多样本验证
        换多个直播间 / 多次进房 / 多时间点验证稳定，别一次成功就开香槟
```

**核心心法**：**每一步都做对照实验，用"排除法"锁定根因，而不是瞎猜。** 那个"空连接能活、发帧就断"的对照实验，是整场逆向的转折点。

## 七、最终形态：一条命令，纯本地拉实时弹幕

四关全打通后，最终交付物是一条命令：

```bash
python kuaishou_live_danmu.py --room <直播间短号> --count 15 --timeout 45
```

它自动完成：

```text
Cookie 缓存读取 → 纯 HTTP 解析 liveStreamId → 纯 Python 生成签名
→ 拿 token → curl_cffi 连 WS 进房 → 心跳保活 → 全类型解码弹幕
```

除了**首次**采集一次设备指纹 Cookie，**运行时零浏览器依赖**。实测在几千人的直播间，进场昵称、礼物、文本弹幕实时滚动输出。

**还有一个隐藏坑**（写出来帮你们省时间）：`liveStreamId` 在页面 `__INITIAL_STATE__` 里有**多处**，必须取 `liveroom.playList[0].liveStream.id`（**当前开播会话**）。取错会订阅到错误房间，只收点赞/在线帧、收不到弹幕——**页面状态字段要取"当前会话"值**。

## 八、合规反思（这段请认真看）

我知道这类技术的边界在哪，全程守着四条红线：

1. **只读公开弹幕流**，不碰任何用户个人隐私（手机号/身份证/住址一概不采集）；
2. **单连接、低频、只读**，不做任何可能压垮服务端的并发抓取，更不做数据倒卖；
3. **不绕过付费/登录墙**，不碰涉及资金、账号安全的功能；
4. 尊重 robots 协议与服务条款，**不提供可直接运行的白嫖脚本**，敏感常量已全部脱敏。

**技术本身是中性的，用来做什么决定了它的性质。** 这套方法论同样能用于：自家业务安全自查、风控对抗研究、协议兼容性测试、性能压测评估等**合法场景**。请把它用在正道上。

## 九、爬虫 / 逆向教学（授人以渔）

想入门协议级逆向，按这个顺序练：

1. **抓包先行**：DevTools / mitmproxy 分清数据走 HTTP 还是 WS、二进制还是 JSON。
2. **找签名/token**：定位动态参数，追它是哪个函数生成的（搜参数名、XHR 断点回溯）。
3. **判断防护等级**：普通混淆 or JSVMP？有无 TLS 指纹 / 设备指纹 / 风控验证码？
4. **协议逐字节比对**：本地编码和抓包帧逐字节对齐，对不上的字段就是突破口。
5. **识别加密算法**：认出 AES/ChaCha/BLAKE/自研魔改，确定 key/iv/模式来源。
6. **本地复现 + 多样本验证**：先单样本跑通，再多输入验证稳定，别一次成功就开香槟。
7. **合规兜底**：控频率、不碰隐私、不碰付费、尊重条款。

工具栈：`mitmproxy` / DevTools / Frida / `curl_cffi`（TLS 指纹）/ protobuf 手工解码 / AST 解混淆 / Node 沙箱。
